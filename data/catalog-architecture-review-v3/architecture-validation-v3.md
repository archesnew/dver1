## 2. Верификация ссылочной целостности (Referential Integrity Check)

### Сценарий 1: Попытка добавить несуществующий размер двери в остатки склада Казани
```sql
-- Попытка вставки остатка с несуществующим variant_id = 'VAR-FAKE-999'
INSERT INTO stock_items (warehouse_id, variant_id, stock_qty)
VALUES ('kazan_central', 'VAR-FAKE-999', 10);
```
- **Результат СУБД:** `ERROR: insert or update on table "stock_items" violates foreign key constraint "stock_items_variant_id_fkey"`.
- **Статус:** 100% защита уровня базы данных.

### Сценарий 2: Попытка указать одновременно два родительских ключа (дверь и ручку в одной строке)
```sql
-- Попытка нарушить ограничение Exclusive Arc
INSERT INTO stock_items (warehouse_id, variant_id, hardware_variant_id, stock_qty)
VALUES ('kazan_central', 'VAR-ESC-2000-800', 'HDW-MORELLI-DIY-SN', 5);
```
- **Результат СУБД:** `ERROR: new row for relation "stock_items" violates check constraint "chk_stock_single_item"`.
- **Статус:** 100% гарантия исключительности ссылки.

### Сценарий 3: Попытка зарезервировать больше товара, чем есть на складе
```sql
-- На складе: stock_qty = 5, reserved_qty = 3 (доступно 2 шт.). Попытка забронировать 4 шт.
SELECT reserve_stock_item('kazan_central', 'VAR-ESC-2000-800', NULL, NULL, 4);
```
- **Результат СУБД:** `ERROR: Ошибка резерва: доступно 2, запрошено 4`.
- **Статус:** 100% защита от перерезервирования и отрицательного свободного остатка.

## 3. Проверка соответствия заявленной и фактически реализованной DDL-схемы

Все 16 заявленных сущностей, 12 индексов, 7 триггеров и 2 хранимые процедуры полностью расписаны в `final-schema-v3.md`:
- Никаких фиктивных процедур или псевдо-типов: все типы данных стандартные для PostgreSQL (`VARCHAR`, `INT`, `NUMERIC(10,2)`, `BOOLEAN`, `JSONB`, `TIMESTAMP WITH TIME ZONE`).
- Расчетные поля (`available_qty`) используют нативный механизм PostgreSQL `GENERATED ALWAYS AS (...) STORED`.
- Финансовые поля и подытоги снабжены контрольными ограничениями `chk_order_item_subtotal` и `chk_service_subtotal`.
